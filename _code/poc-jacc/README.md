# poc-jacc

A proof of concept for a tiny scripting language: a hand-written lexer, a
LALR parser generated by [jacc](https://repo1.maven.org/maven2/org/xbib/jacc/)
from a `.jacc` grammar file, and a compiler that turns the parsed AST into
real JVM bytecode with [ASM](https://asm.ow2.io/).

`com.example.Main` is a small Unix-style filter: it reads a script from
standard input and writes the compiled class's bytecode to standard output.
Piping this script in:

```
total = 0;
i = 10;
while (0 < i) {
    total = total + i;
    i = i - 1;
}
total
```

produces a class named `Tiny` with a `public static int run()` method
returning `55`, the value of the trailing `total` expression — see
"Language syntax" below for why there's no `result = ...;` or `return` here.
The generated class also has a real `public static void main(String[])`
that calls `run()` and prints the result, so it can be launched directly
with `java Tiny`, no extra tooling needed.

## Prerequisites

- JDK 21 (the project targets `--release 21` via `maven.compiler.source` /
  `maven.compiler.target` / `maven.compiler.release`).
- Maven 3.9+, only to *build* the compiler. Once `target/poc-jacc.jar` is
  built, running it needs nothing but the JDK — see "Without Maven" below.
- Network access to Maven Central the first time you build. Dependencies
  resolved from there include `org.xbib:jacc:3.0.0` (the parser generator,
  a plugin-level dependency only), `org.ow2.asm:asm:9.7.1` (the bytecode
  library used by `TinyCompiler`), `org.junit.jupiter:junit-jupiter` (test
  scope), `com.spotify.fmt:fmt-maven-plugin` (source formatting), and
  `maven-shade-plugin` (bundling the fat jar).

## Build and run

```bash
mvn clean package
```

This also generates `TinyParser.java` and `TinyTokens.java` from the grammar
(see "How the grammar gets compiled" below) before compiling anything else,
and reformats `src/main/java`/`src/test/java` with `fmt-maven-plugin` (see
"Code style" below).

It produces two jars in `target/`:

- `target/poc-jacc.jar` — a self-contained "fat" jar built by
  `maven-shade-plugin`, with ASM's classes merged in. Runnable with a plain
  `java -jar`, no classpath needed.
- `target/original-poc-jacc.jar` — the thin jar (this project's classes
  only), kept alongside by the shade plugin. Not directly runnable on its
  own; see the note at the end of this section.

### With Maven

```bash
mvn exec:java < script.tiny > Tiny.class
```

This defaults to `com.example.Main` (configured at the `exec-maven-plugin`
level in `pom.xml`), so no `-Dexec.mainClass` is needed. It compiles against
`target/classes` directly, so it's the fastest loop while developing this
project itself, but it does need Maven and the full reactor build.

### Without Maven

Once `target/poc-jacc.jar` is built, that's the only file needed — no `mvn`,
no classpath juggling. A full transcript:

```console
$ cat <<'EOF' | java -jar target/poc-jacc.jar > Tiny.class
total = 0;
i = 10;
while (0 < i) {
    total = total + i;
    i = i - 1;
}
total
EOF

$ java Tiny
55
```

The first command is the compiler: script text goes in over stdin, `Tiny`'s
bytecode comes out over stdout, redirected straight into `Tiny.class`. The
second command runs it: `java <ClassName>` finds `Tiny.class` in the current
directory and calls the generated `main(String[])`, which prints `run()`'s
value — no reflection, no loader, no jshell, just the plain `java` launcher
against a `.class` file it already knows how to run.

### A note on the thin jar

`java -jar target/original-poc-jacc.jar` will **not** work: that thin jar
only contains this project's own classes, and the JVM throws
`NoClassDefFoundError: org/objectweb/asm/Opcodes` because ASM isn't on the
classpath. That's exactly the jar the fat `target/poc-jacc.jar` exists to
replace for standalone use. If you do need to run against loose classes
(e.g. `target/classes`, during development), ASM has to be added to the
classpath explicitly:

```bash
java -cp "target/classes:$(find ~/.m2/repository/org/ow2/asm/asm/9.7.1 -name '*.jar')" com.example.Main < script.tiny > Tiny.class
```

## Language syntax

A script is zero or more statements followed by exactly one **tail
expression** with no trailing `;`. There's no `return` statement and no
special variable name; the tail expression's value — identified purely by
its *position*, last, with no semicolon — is the script's result, the same
idea as the last expression in a Rust block.

Grammar, in the same shape as `TinyParser.jacc`:

```
program : stmt* expr
stmt    : IDENT '=' expr ';'
        | 'if' '(' expr ')' stmt
        | 'while' '(' expr ')' stmt
        | '{' stmt* '}'
expr    : NUMBER
        | IDENT
        | expr '+' expr
        | expr '-' expr
        | expr '<' expr
        | '(' expr ')'
```

A few things follow from that shape:

- **Nested `{ ... }` blocks (`if`/`while` bodies) do not have a tail
  expression** — only the top-level `program` does. A block is just zero or
  more statements; it can't itself produce a value. To get a value out of a
  branch or loop, assign it to a variable and reference that variable in the
  program's own tail expression, exactly like `total` in the example above.
- A script can be a single bare expression with nothing else, e.g. `40 + 2`
  is a complete, valid script (the `expr` alternative of `program`) that
  compiles to a `run()` returning `42`.
- Assignment is a statement, not an expression: `x = 5;` cannot be nested
  inside another expression (there's no `x = (y = 5);`).
- Every value is a plain `int`. `<` is the only comparison operator, and it
  produces `1` for true or `0` for false, C-style — there is no boolean
  type.
- **Operator precedence is not what you'd expect from C or Java**: `<`
  binds *tighter* than `+`/`-`, the reverse of most languages. Concretely,
  `1 + 2 < 3` parses as `1 + (2 < 3)`, not `(1 + 2) < 3` — it evaluates to
  `2` (since `2 < 3` is `1`, and `1 + 1 = 2`), not `0`. This falls directly
  out of the `%left` precedence declarations in `TinyParser.jacc`, where
  later declarations bind tighter:
  ```
  %left '+' '-'
  %left '<'
  ```
  `+` and `-` are both left-associative at the same precedence (`10 - 3 - 2`
  is `(10 - 3) - 2 = 5`), and so is `<`.
- Referencing a variable that was never assigned earlier in the script is a
  compile-time error (`RuntimeException: Undefined variable: <name>`,
  thrown by `TinyCompiler` while walking the AST, before any bytecode runs).
- There's no `else`; `if (cond) stmt` only ever has a "then" branch.

## How the grammar gets compiled

`src/main/resources/TinyParser.jacc` is not Java source; it's fed to the
`jacc` tool, which emits real `.java` files. That happens automatically
during the `generate-sources` phase, wired up in `pom.xml`:

1. `exec-maven-plugin`'s `generate-tiny-parser` execution runs
   `org.xbib.jacc.Jacc` (declared as a plugin-level dependency, not a
   project dependency, so it never ends up in the final jar) against
   `TinyParser.jacc`, writing `TinyParser.java` and `TinyTokens.java` to
   `target/generated-sources/jacc/com/example/`.
2. `build-helper-maven-plugin`'s `add-jacc-source` execution registers
   `target/generated-sources/jacc` as an extra source root, so the generated
   files compile alongside the hand-written sources in `src/main/java`.

Both executions are bound to `generate-sources`, so `mvn compile`,
`mvn package`, `mvn exec:java`, and IDE builds all trigger generation first.
Nothing under `target/generated-sources` is checked in; delete `target/` and
rebuild any time you want to regenerate from scratch.

### Grammar file conventions that matter

The `.jacc` format looks like yacc but has its own rules, discovered by
reading the `org.xbib:jacc` source (there's no upstream README):

- `%{ ... %}` at the top becomes raw text emitted **before** the generated
  `public class TinyParser { ... }` declaration. It must contain only
  `package`/import statements, not a class body — jacc emits its own class
  wrapper, so anything else here would double-declare the class.
- Fields, the constructor, and helper methods that need to live *inside* the
  generated class go **after** the second `%%`, not in the `%{ %}` preamble.
  That trailing block is spliced in verbatim right before the class's
  closing brace.
- `%package com.example` is required for both generated files to share the
  same package. Without it, `TinyTokens.java` (produced by a separate writer
  than `TinyParser.java`) is emitted with no package statement at all.
- `%class TinyParser` / `%interface TinyTokens` are required. The bundled
  `Jacc` CLI never calls its own `setName(...)`, so without these directives
  the class/interface default to `nullParser` / `nullTokens`.
- `%type <List<AST.Stmt>> stmt_list` does not parse — jacc's type parser
  doesn't support nested generics. Use the raw type `%type <List>` instead;
  it's safe here because `$$` is always stored as `Object` (see below), so
  the declared `%type` only affects casts applied when *reading* `$1`, `$2`,
  etc., not when writing `$$`.
- `%semantic Object : lexer.getSemanticValue()` tells jacc to store semantic
  values as `Object` (matching every AST node type, `Integer`, and `String`
  used across the grammar) and to fetch each token's value by calling
  `TinyLexer.getSemanticValue()`.
- The generated `parse()` method reads the *current* token via
  `lexer.getToken()` before doing anything else; it does not fetch one.
  Callers must prime the lexer with one `nextToken()` call first — see
  `Main.compile()`.

## Code layout

| File | Role |
| --- | --- |
| `src/main/resources/TinyParser.jacc` | Grammar source; compiled by jacc into `TinyParser.java` / `TinyTokens.java` during `generate-sources`. |
| `src/main/java/com/example/TinyLexer.java` | Hand-written lexer implementing `TinyTokens` (generated interface). |
| `src/main/java/com/example/AST.java` | Sealed `Node`/`Expr`/`Stmt` hierarchy of records, plus the top-level `Program` record (statements + tail expression). |
| `src/main/java/com/example/TinyCompiler.java` | Walks the AST and emits JVM bytecode with ASM: `run()`, plus a `main(String[])` that calls it and prints the result. |
| `src/main/java/com/example/Main.java` | Compiler entry point: script in via `InputStream`, bytecode out via `OutputStream`. |

## Tests

`src/test/java/com/example/MainCompileTest.java` covers `Main.compile()` the
same way the CLI uses it: a script's bytes go in through an in-memory
`ByteArrayInputStream`, the compiled bytecode comes out through a
`ByteArrayOutputStream`, and each test loads that bytecode with a throwaway
`ClassLoader` to invoke `run()` and check the result. One test drives
`Main.main()` itself with `System.in`/`System.out` redirected, to confirm
the actual command-line pipe contract works, not just the underlying method.
Another invokes the *compiled class's* generated `main(String[])` with
`System.out` redirected, confirming the printed value matches `run()` — the
same thing `java Tiny` relies on.

A compiled script can contain a genuine infinite loop (`infiniteLoopIsGuardedByTimeout`
checks exactly this), and the JVM has no safe way to force-stop a thread
stuck in a tight, non-blocking loop. Every invocation therefore runs on an
explicitly **daemon** thread with a bounded `Future.get(timeout, ...)`: on
timeout the test fails cleanly instead of hanging, and the abandoned thread
can never block JVM shutdown since daemon threads die with the process.

Run the suite with:

```bash
mvn test
```

## Code style

`com.spotify.fmt:fmt-maven-plugin` (wrapping `google-java-format`) is bound
to the `format` goal with no explicit phase, so it defaults to
`process-sources` and runs automatically on every build, before `compile`.
It only touches `src/main/java` and `src/test/java`; the jacc-generated
sources under `target/generated-sources` are untouched.
